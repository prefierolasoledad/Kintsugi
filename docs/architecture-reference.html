How Kintsugi works

A secondhand marketplace, explained from the browser down to the database — what each piece does, why it was built that way, and which numbers were measured rather than claimed.

Architecture reference 32 decision records 35 test suites 1,263 assertions passing

The idea

A marketplace where the damage is part of the description

Kintsugi is the Japanese craft of mending broken pottery with gold, so the break becomes part of the object's history instead of something to hide.

The site sells secondhand furniture, clothing and objects, and it takes that idea literally: condition is disclosed, not glossed over. A chair with a repaired leg says so. Almost every item is one of a kind — one chair, one jacket, one mended plate — and that single fact shapes more of the engineering than anything else on this page.

Because if there is only one chair, the hard problem is not counting stock. It is making absolutely certain that two people who click "buy" at the same instant cannot both get it. That constraint comes back again and again below, in slightly different clothes: two buyers and one chair, two refunds and one order, two workers and one notification.

What you can actually do on it

Browse and search a catalogue, save things to a wishlist, buy with a card, get refunded when a seller can't send an item, leave a review if you actually bought the thing. As a seller: list items with photos, verify your identity, mark orders shipped. As a moderator: see everything, remove listings, suspend accounts, and answer "did that customer get their email?"

Money now completes its whole circuit. A buyer pays the platform; the platform pays the seller once the item has been delivered and a return window has closed; and a buyer who receives something broken can ask for their money back from the order itself, which the seller answers and a moderator settles if they disagree.

That last sentence was the largest gap in this document for most of the project's life, and it is worth saying why it took so long. The refund machinery existed early — per-line, guarded against over-refunding, settled by webhook. What was missing was never the plumbing. It was deciding who is allowed to say yes, which is a product question wearing an engineering costume.

The shape

Six moving parts, and only one of them is allowed to say no

There are two Node programs, not one, and the split is the most important structural decision in the system. The browser never talks to the API directly. It talks to the Next.js server, which forwards the request onward without interpreting it.

That forwarding server is called a BFF — a backend for the frontend. It holds no business rules at all. Every rule lives in the Express API, which means someone who bypasses the website entirely and pokes the API with a script gains nothing: the same checks run either way. A greyed-out button is a courtesy; the server re-checks.

The rule this buys

Redis and Kafka are allowed to lose everything they hold. Rate-limit counters can evaporate; the cache can be cold; the broker can be empty. None of that loses an order, a notification, or money — because the record of all three lives in Postgres, and the other two are only ever carrying work in progress.

A request

What happens between the click and the answer

Signing in gives the browser two cookies, and they do very different jobs. Neither can be read by JavaScript, so a script injected into the page cannot steal a session.

The two cookies
CookieWhat it isLastsStored in the database as
access A signed token the API can verify without a database lookup 15 min Not stored at all — it is self-proving
refresh A long random string, good only for getting a new access token 30 days A SHA-256 hash, never the value

Hashing the refresh token matters for the same reason hashing a password does: if the database leaks, an attacker gets hashes, and a hash cannot be presented as a cookie. That refresh token is every bit as good as a password for impersonating someone, so it gets the same treatment.

The renewal nobody sees

Access tokens expire every fifteen minutes, which would mean being logged out constantly. Instead the BFF handles it: when the API says "expired", the BFF quietly renews and retries the original request. The browser only ever sees the successful answer.

What happens if a refresh token is stolen

Every renewal issues a new refresh token and marks the old one used. So if a token that has already been used shows up again, only one thing can explain it: a copy is in someone else's hands. The system does not try to guess whose — it kills the entire session family. The real user logs in again. The thief gets nothing that lasts.

The hard problem

Two buyers, one chair

Here is the bug that a marketplace of unique objects must never have. Checking stock and then taking it looks obviously correct and is obviously wrong:

  • Two requests arrive at the same moment.
  • Both read the chair. Both see quantity 1.
  • Both decide they may proceed.
  • Both write quantity 0. The chair sells twice.

The window is tiny — a few milliseconds — which is exactly why it survives testing and appears in production. The fix is to make the database itself hand out the answer, one caller at a time.

The same shape, five more times

Once you can see this pattern you can see it everywhere in the codebase, and that repetition is deliberate — one idea learned once, applied wherever it fits. The two most recent features in the system, seller payouts and buyer returns, needed no new idea at all: both are the chair again, in different clothes.

One decision, made atomically, before any outside call
WhereWhat could go wrong twiceHow it is claimed

Refunds More refunded than was paid Refund headroom claimed the same way

Returns Two requests on one item, answered separately A unique row per order line, and the insert is the request
The rule, stated once

One system decides, atomically, and the outside call happens only after that decision is durable. Never the other way round — because if you call Stripe first and then record it, a crash in between leaves money moved and no record of it.

Telling people things

The notification pipeline, which is most of the machinery

Eleven things can happen that a person should hear about: an item sold, an order shipped, a refund issued, an account suspended. Each one has to reach the right person, on the channels they agreed to, exactly once.

The naive version is to save the notification and then send the email. That is two writes to two systems with no transaction around them, and a crash in the gap is silent: either a notification nobody was told about, or an email about something that got rolled back. Nothing anywhere records that the pair was supposed to be atomic.

The seam this closes

So the event is written into an outbox — an ordinary table — in the very same transaction as the notification. They commit together or not at all. A separate small program, the relay, reads committed outbox rows and publishes them onward. A crash anywhere now leaves work visibly unfinished rather than quietly lost.

Why waiting happens on a separate queue

When a send fails for a reason that might fix itself — a timeout, a server having a bad minute — the obvious move is to wait and try again. The obvious move is wrong. A worker that sits waiting holds up every other message queued behind it, so one person with a dead phone number would delay everybody else's notifications.

Instead the message is pushed onto a separate queue with a built-in delay, the worker moves on, and something else picks it up later. Three rungs — five seconds, one minute, fifteen minutes — and then it lands in a dead-letter queue where a human can look at it.

Failures that cannot fix themselves never enter that ladder at all. A rejected address, a deleted account, or a recipient who replied STOP is permanent. Retrying those is how a sender's reputation gets burned, and in the case of an opt-out it is also unlawful.

Consent, before anything is sent

Each of the eleven events has a default for each channel, and each person can override it. Two of them default to SMS — a refund, and an order that cannot be sent — because in both cases money moved and the person needs to know away from a screen. A review notification does not clear that bar.

  • Nothing is texted to an unverified number. A six-digit code, valid ten minutes, five guesses, then it is spent.
  • A parcel's delivery phone is never reused for messaging. It is often a third party — a gift, a workplace, a relative — who never agreed to anything and cannot unsubscribe.
  • Quiet hours defer rather than drop. A message caught at 3am is parked and sent when the window opens, once, by exactly one server.
  • A daily cap per person, as a circuit breaker against bugs rather than as a preference.

The numbers

Measured, including the unflattering parts

This project has a rule about performance: measure it, don't claim it. Five scripts exist to make the claims checkable, and the database-transaction counts come from Postgres's own counters rather than from the application, because an application counter measures what the code believes it did.

The notification pipeline was built partly to scale. So the honest question is: does it? The answer is more interesting than a yes.

The rest of the measurements

Each of these comes from a script in the repository that can be re-run, and each one shows the thing failing before it shows it working — a number with no failing baseline next to it is hard to trust.

The one worth pausing on

A worker was killed outright — no warning, no cleanup — with 2,215 of 3,000 messages still outstanding. The survivors finished all 3,000, with zero duplicates and zero losses. Two mechanisms had to hold at once for that: the position marker is only advanced after a message is handled, so a crash re-delivers rather than skips; and the ledger refuses the second claim, so a re-delivery cannot become a second email. Either one alone fails — advance-first loses messages, no-ledger doubles them.

Swappable parts

Every outside service sits behind a seam

Seven things live outside: taking payments, paying sellers, checking identity documents, sending email, sending texts, storing files, and carrying notifications between processes. Each one is reached through a single small module with two implementations behind it — the real service, and a stub — chosen by one environment variable.

The stubs are not placeholders for unwritten code. They are what the automated tests run against, which is why the whole purchase, refund and verification flow can be exercised with no credentials at all — and why someone contributing from a fork of the repository, who cannot read its secrets, still gets a meaningful green test run.

The API prints which of each it is using when it starts, and the interface says so on screen where a user could be misled. A stub that silently looks real is worse than no stub at all.

Identity documents are the sharpest case

A government ID is exactly the kind of data that turns a database into something worth attacking, for no product benefit. So the system stores a reference to somebody else's verification result and never the document — and with the real provider the document never reaches this server in the first place. Switching provider does not merely swap an implementation; it shrinks what the application is capable of leaking.

The data

Twenty-eight tables, in six groups

Postgres is the only thing that is ever authoritative. Everything else in the system can be rebuilt from it.

What is stored, and the one rule that governs each group
GroupTablesThe rule that matters
People users · refresh_tokens · email_verification_tokens · password_reset_tokens · phone_verifications Every credential is hashed. One account type — selling is a capability you switch on, not a different kind of user
Selling seller_profiles · kyc_attempts · categories · listings · listing_images Listings are never really deleted — a past order has to stay readable, so they are marked removed instead

Two details that explain a lot of the rest

Preferences store deviations, not state. An absent row means "use the default". The alternative — a row per person per event per channel, created at signup — would mean that adding a twelfth event type requires touching every account in the database before it can be sent at all, and would store thirty-three rows per person to record that they never opened the settings page.

A delivery record outlives the account it was for. There is deliberately no foreign key from a delivery to a user, so "this was sent to an account since deleted" remains a real, answerable question.

Confidence

How it is tested, and what testing means here

Thirty-five suites, 1,263 assertions, and nothing is mocked. The tests drive a real Postgres, the real Express API, and a production build of the site under a real browser — on the view that the bugs worth catching live in the seams between the pieces rather than inside any one of them.

That has a cost, and it is paid deliberately: the suite needs a database, a Redis, and both servers running, and it takes about thirteen minutes.

Testing a message broker without requiring one

Adding Kafka to every test run would slow the pipeline and give contributors one more thing to install. So the notification transport has the same shape as the payment and identity seams: by default the relay hands events straight to the same worker functions, in-process, no broker involved. Preference resolution, the duplicate guard, template rendering, the provider calls — all of it runs for real. Only the wire is absent.

The handful of claims that genuinely need a broker live in one gated section, and when there is no broker that section skips loudly and names what went unproven rather than passing quietly. A section that reports green for something nobody ran is worse than no section, because it gets believed.

Found by finally running it

That gated section had never actually executed. The first time it did, it failed — it produced its messages after subscribing and lost a race with the broker's group assignment, which no amount of waiting would have fixed reliably. Gated code that has never run is not tested; it is only written.

Running it

One image definition, several programs

A single Dockerfile describes every process the system can run, each as its own build target: the API, the website, the database with its backup tooling, the notification relay, and the channel workers. The relay and the workers are separate programs precisely so they can be scaled and can fail independently of the website.

Bringing everything up is one command. Two of the containers exit immediately, and that is correct — one applies pending database migrations and one creates the file-storage bucket, both finishing before the API starts. Doing either of those at API startup is the usual shortcut, and it breaks the moment there is more than one copy of the API racing to do it.

Optional pieces sit behind named profiles, so a plain start-up stays small: the standby database, the message broker with its relay and workers, and one-off tools like seeding and backups.

And on a cluster, where the database can be replaced

Compose can start everything on one machine and it can do nothing about a machine that dies. So the same images also have Kubernetes manifests, and the interesting part is what happens to Postgres: it is not a workload written by hand here but a CloudNativePG cluster, which is an operator whose whole job is knowing how to promote a replica when the primary stops answering.

That claim was tested rather than assumed. Deleting the primary's pod on a local cluster produced a promoted replica, and a write submitted afterwards — a real signup, through the website, to the database — succeeded. The figure worth noticing is the last one:

2 of 2 rows found in the promoted instance: one written before the kill, one after
0 API restarts needed to reconnect
199s promotion, on one laptop node with no spare memory
Why the restart count is the number to read

Any orchestrator will restart a pod, and a restart would have hidden the question. The connection pool inside the API had cached an address that stopped being the primary — and it recovered on its own, because it connects to a name the operator moves rather than to an instance. Had it needed bouncing, the demonstration would still have "passed" while concealing the thing worth demonstrating.

Two things are honest to say about it. 199 seconds is slow, and it is printed rather than smoothed over: a promotion is a short automatic outage, not an invisible one, and the site did return errors during the window. And this ran on a laptop, not a cloud. A manifest that applies locally can still be wrong about a load balancer.

One scheduled job, and five that stayed where they were

A cluster brings a scheduler, and the obvious move is to take every background loop in the application and make each one a scheduled job. That would have been a step backwards. Five recovery sweepers run inside the API — returning expired holds to stock, settling payments whose request died, sending messages that quiet hours parked — and each of them claims its work with the same conditional write the rest of this document is about. Which means several copies divide the work rather than repeating it, and one scheduled job would have serialised what currently parallelises.

Exactly one thing became a scheduled job: finishing a payout that was claimed and never transferred, because the provider timed out. It is scheduled for a reason that has nothing to do with tidiness — it moves money to somebody else. A job has an exit code, a start time and a record; a loop inside the process serving checkout has only log lines, and shares a thread pool with people trying to buy things.

Honesty

What is deliberately not built

A description that only lists what works is a sales document. These are the real edges, and most of them are known trade-offs rather than oversights.

And one that is worth naming as a pattern

Three pieces of the notification pipeline had to be built after the phase that argued for them was declared finished: the retry ladder was designed and never wired up; quiet hours shipped as a silent drop rather than a deferral; and the sweeper that rescues a half-finished send went unbuilt through four phases. Each was caught by writing something that measured the claim rather than restating it.

Vocabulary

The handful of words that do the most work

Seam
A single small module that stands between the system and an outside service, with a real implementation and a stub behind it. Changing provider means editing one file.
Outbox
An ordinary database table that events are written into, in the same transaction as the thing they describe, so the pair cannot come apart.
Relay
The small program that reads committed outbox rows and publishes them onward. Several can run at once without publishing anything twice.
Ledger
One row per notification per channel, written before the provider is called. A repeat attempt collides with that row and stops, which is what makes an at-least-once queue safe to point at a phone.
Claim
A single write whose success is the permission to proceed. Used instead of checking and then acting, because two callers can both pass a check and only one can win a write.
Suppressed
A delivery that was deliberately not sent — the channel was off, there was no verified number, it was quiet hours. Recorded rather than dropped, so "why did nothing arrive?" has an answer.
Sweeper
A timer that recovers state nothing in the normal request path will ever reach again: expired holds, unpaid orders, parked messages, half- finished sends, spent outbox rows.
